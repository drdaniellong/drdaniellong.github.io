# What This Project Is (Plain-Language Overview)

**If you're a search committee member, hiring manager, or anyone without a
SQL or Banner background, start here rather than the technical README.**

## The problem this solves

Every college and university that receives federal financial aid is
required to report detailed enrollment data to the U.S. Department of
Education through IPEDS (the Integrated Postsecondary Education Data
System) — specifically, a survey called the 12-Month Enrollment (E1D)
component. That means turning raw student records into a very specific,
federally defined format: one row per student, with standardized codes
for race/ethnicity, enrollment status, full-time/part-time status, and
more, plus a summary of total instructional activity across the
institution.

Most colleges and universities run their student records through
**Ellucian Banner**, a widely used higher-ed database system built on
Oracle. Getting from "raw Banner data" to "a file IPEDS will accept" is a
real technical task — one usually handled by an institutional research
(IR) office.

## What I built

This project is a complete, working simulation of that entire pipeline,
built and tested end-to-end without needing access to a real
institution's live student data:

1. **A fake but realistic Banner database** — I wrote SQL to create
   simplified versions of the actual Banner tables involved, then
   generated 100 fake student records with realistic, randomized
   characteristics (enrollment status, demographics, course load, etc.).
2. **SQL extract scripts** that query that data — written in both
   standard Oracle SQL (runnable via SQL\*Plus or SQLcl) and as
   **Argos** DataBlocks (Argos is a common reporting front-end many
   colleges, including where I'm applying, use on top of Banner) — and
   produce two files matching the exact format IPEDS requires.
3. **An R script** that feeds those two files into a public R package
   (`IPEDSuploadables`) to produce the final, submission-ready file.
4. **Documentation** of the whole process, including a checklist of
   real-world quality-control steps (like sanity-checking totals against
   a prior year's submission) that any institution would need to run
   before trusting this against real student data.

## Why this matters for an IR role

I built this specifically to demonstrate direct, working familiarity with
the exact tools and file formats an institutional research office uses
day to day — Banner's data structure, Oracle SQL, Argos, and the IPEDS
reporting format — rather than just describing that experience in the
abstract. Every piece of "customize this for your institution" logic is
clearly marked in the code, because that's the honest reality of this
kind of work: the general approach is portable across schools, but the
specific codes always have to be confirmed against each institution's own
setup.

## A note on the data

**No real student data was used anywhere in this project.** All 100
"students" are randomly generated by a seeded script — there is no way to
trace any row back to a real person. This was a deliberate choice: it let
me build and fully test the entire pipeline before ever touching a real
Banner connection, which is exactly the kind of careful, methodical
approach I'd bring to handling real, FERPA-protected student data in an
actual IR office.
